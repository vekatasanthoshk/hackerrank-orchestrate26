## How the system is scored

`code/evaluation/main.py` runs the full auditor on three suites and compares to expected outputs:

* **Public samples (32):** `dataset/sample_deletion_requests.csv` vs `dataset/sample_output.csv`.
* **Custom cases (7):** `code/evaluation/custom_cases/*.json`, requests against the real
  challenge evidence for behaviours the samples do not cover (the samples contain no
  NOT_APPLICABLE case at all). Expected answers are hand-derived from raw evidence lines, but
  they read the same evidence as the engine, so they cannot catch a misreading we share.
* **Synthetic fixtures (4):** `code/evaluation/fixtures/`, a small hand-built dataset (fictional
  people at `example.test`) whose correct answers follow from how it was constructed. The
  expected steps were written from the problem statement and `deletion_rules.csv` before the
  engine was run on these files. This is the suite that is independent of the engine.

Six intent probes are scored as well (264 hand-written texts). Each was written before the
rule change it measured, committed before it was scored, and scored once as held-out; five were
then used to fix the rules and are now **dev sets**. Only the last, `intent_probe_heldout_v6.json`
(40 texts, written after the rules were frozen in commit `d30cd18`), is still held out. See
"Intent probes" below for each probe's first score.

Metrics:

| Metric | Definition |
|---|---|
| status accuracy | `deletion_status` exact match per case |
| step precision / recall / F1 | multiset match on (phase, system_id, resource_id, operation, state) |
| field accuracy | for gold steps aligned to a predicted step with the same (system, resource, operation): phase, state, step_no, evidence_id |
| evidence_id accuracy | cited evidence correct among aligned steps (COMPLETE checks and findings cite files; INCOMPLETE remediation / verification must be `""`) |
| sequence exact | whole step array identical (all 7 fields, in order) |
| sequence LCS | longest common subsequence of step keys / max(len(pred), len(gold)) |

### Reading the numbers

* **Status, precision, phase/state, evidence:** all 1.000 on the samples. Every step we emit is
  in the gold answer, and every aligned citation picks the same file as the gold answer.
* **Recall 0.870:** every missing gold step is a *verification* step for a resource that no
  participant-visible artifact ties to the subject:
  bare-404 account read-backs with no identifier (`account_001/002/004/008/010`, `account_3136`,
  `account_6440`, `account_4857`, …), anonymized analytics profiles that never carried an identifier
  in any file (`analytics_901`, `analytics_1895`, `analytics_9406`, …), and two audit records that
  appear in no evidence file at all (`audit_record_6645`, `audit_record_5569`). We do not guess them.
* **step_no / sequence:** these follow from recall. A missing verification step shifts the
  numbering of the steps after it, so sequence-exact is 0.41 even though the LCS order agrees
  wherever both lists have the step.
* **The samples flatter us.** All 32 sample cases were available while the rules were written,
  so 1.000 status / precision there is an upper bound. The synthetic fixtures (4/4, written
  before the run) and the final held-out intent probe (v6: 34/40 with rules only) are the better guide to
  behaviour on unseen inputs. Expect evaluation recall at or below the sample figure.

What each round fixed, as categories rather than phrases: reversals of a deletion request
("I've changed my mind", "cancel my deletion request", "reopen my account") and per-language
"I don't want you to delete" negations (v2, v3); deletions that are only *mentioned*, in
informational questions, conditional threats and abandoned intentions (v4); deletion verbs aimed
at something other than the person's own account or data, or at someone else's account (v5).
Across all of it the 409 request texts of the dataset, custom cases and fixtures keep the same
labels.

**What the numbers say.** Every round fixed what it was tuned on, but each fresh set still found
new unsafe errors: 7, 7 and 5 of the 20 non-deletion texts in v4–v6. The v6 misses are a field
deletion with "the account itself is fine", a past-tense statement ("I deleted my saved card
myself"), a Spanish question without an interrogative opener, a German "only the old address,
the account stays", and "never mind my last message about deleting everything". **The keyword
rules are reliable on the dataset's phrasing but not safe on open-ended text.** That is why the
model is meant to be the primary classifier, with the rules only able to veto a model DELETION
(explicit keep / reversal cues) or decide when injected instructions were found. We stopped
tuning at v6 rather than fit a seventh set. The submitted run still uses the rules, because no
key has reached a session.

**Where the intent rules came from.** The previous rule list contained four cues lifted from
evaluation texts ("misspel", "reset the login", "invoices … records", "out of date"). The
rule layer is now organised by the request categories the problem statement names (access,
export, correction, opt-out, login help, billing), plus explicit "keep my account" and negation
cues in all six request languages. The four lifted cues are gone. They were redundant: each of
those texts also carries a generic keep cue ("leave the account active", "without removing",
"leave my profile", "do not close"). Across all 405 distinct request texts (evaluation,
samples, custom) the rewrite changes **0** labels. That the 10 NOT_APPLICABLE predictions
match the dataset's own `CLASSIFY_REQUEST` rows is a consistency check, not evidence of
generalisation; the held-out probes are that evidence.

**Coverage.** 254 of the 508 deletion answers contain no `account_service` step (269 before
the identifier-field fix in #23), and 66 COMPLETE answers consist of a single check. Three scans
explain it:
* for 252 of the then-269 cases, the subject's identifiers appear in the evidence only on
  non-account records, and no account read-back carries any of them;
* the only field in any record that points at another resource is `source_resource_id`
  (search → account), which is already followed;
* the 16 account checks missing from the sample answers each appear in exactly one place: a
  deletion-worker `DELETE_RECORD` claim within about 75 minutes of that request's `reported_at`.
  That is the link the dataset intends, and the batch inference (#4) uses it where it is
  unambiguous. 13 of the 16 sit in report batches where 2–6 unlinked claims compete, and the
  claim order matches no request attribute, so assigning them would be a guess.
A wider time window (claims up to 15 minutes *after* the report) would add two sample checks
(`account_002`, `account_008`; recall 0.870 → 0.881) but changes **none** of the 518 evaluation
answers, so it would only flatter the sample score. It was measured and reverted. If an
unlinked account still exists, its case is wrongly COMPLETE, and we cannot detect that.

## Automated tests

`python3 -m unittest discover -s code/tests -v` runs 54 tests in ~15 s. `test_robustness.py`
attacks each guard listed in `docs/SECURITY.md`:
* SQL `ATTACH`, `PRAGMA` and hostile table names;
* path traversal, bad ids, corrupt, missing and badly timestamped manifest rows;
* injected keys and ids in model output;
* prompt injection: an injected DELETION with and without a "keep my account" cue, in three
  languages, and an injected NOT_DELETION that tries to suppress a real deletion request;
* the multilingual keep veto;
* malformed, truncated (`max_tokens`) and refused model answers;
* **the real `anthropic` SDK against a local fake API (no network, no key)**: request shapes
  for intent (JSON schema, effort, no sampling parameters) and vision (PNG image block, native
  PDF document block, refusal fallbacks); refusal, truncation and HTTP 400 / 429 / 529 errors
  reaching the code as the exception types it catches; downscaling of an oversized image;
  a failed refresh keeping the earlier transcription;
* unknown states that must never count as proof;
* catalog links kept or dropped by what the record itself prints;
* unknown and upper-case emails, timezone offsets, an invalid `audit_at`, and duplicate or blank case ids.

`test_pipeline.py` covers all six log dialects, the sha256 email-hash rule for all 850 users,
identifier normalisation and the identifier fields found in the evidence, historical-email and
decoy resolution, state interpretation (404s, hits, enabled flows, restore decisions, free-text
PII, `[REDACTED]` bodies, attachment / secondary-identifier categories read from record
content), the latest-observation cross-checks, multilingual intent, policy mapping, the case_11
ordering, the sample score floor (status 1.000, precision 1.000, recall ≥ 0.86), all custom
cases, and a full 518-case run checked for contract validity and run-to-run determinism.

The SDK tests show that our requests are accepted by the SDK and that its response objects are
handled. They are **not** a live run. Whether the real models extract the screenshots
correctly, and what real latency, rate limits and token use look like, is still unmeasured.
