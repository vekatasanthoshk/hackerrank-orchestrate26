User Prompt (verbatim, secrets redacted):
What the data tells you (read this before you prompt anything)
This is mostly a deterministic problem, and the LLM is a thin layer on top. The evidence files normalize to the same observation shape. For example, `evidence_03` (a shift-handover .txt) has lines like:

```
2026-10-01T12:00:00Z | search_service | search_052 | SEARCH_INDEX_ENTRY | FOUND | novak.tomasz@icloud.com
```

That gives you a timestamp, system, resource, data category, observed state and identifier. The other formats (SQL replicas, JSON bundles, logs, PNG screenshots, PDFs) carry the same facts in different shapes. Once everything is in one table, each case reduces to five steps: resolve identities, filter evidence captured at or before `audit_at`, take the latest state per resource, apply `deletion_rules.csv`, then emit steps in a fixed order.
Key numbers:

* Requests: 518 to answer and 32 samples. The samples split 22 INCOMPLETE, 10 COMPLETE and 0 NOT_APPLICABLE, so your intent classifier gets no validation from the samples. Build custom eval cases there.
* Evidence: 95 files. That’s 28 JSON, 26 logs, 24 SQL, 11 PNG, 4 PDF and 1 TXT. Only the 15 images and PDFs need a VLM.
* `system_activity.csv`: 4,012 rows of claims. 721 are FAILED and 376 PARTIAL. A `DELETE_RECORD … SUCCESS` proves nothing on its own. Evidence readbacks are the source of truth.
* Identity: 850 users and 306 historical identity changes. Request emails can be historical. Evidence shows emails in mixed case (`CHOI.JIHOON94@GMAIL.COM`), and records also refer to users by `user_id`, `email_hash` or phone.

Sample `case_11` confirms how steps are ordered and what they cover:

* Findings: ordered by operation (REMAINING → EXPOSED_PII → ACTIVE_DATA_FLOW → RESTORE_RISK), then by `system_id`, then `resource_id`.
* Remediation: DISABLE_FLOW → BLOCK_RESTORE → DELETE → REDACT → ANONYMIZE.
* Verification covers every relevant resource, including already-compliant ones. For example, `account_4248` gets VERIFY_ABSENT and the retained security audit record gets VERIFY_PRESENT even though neither had a finding.
* Evidence IDs: INCOMPLETE remediation and verification steps use `""`. COMPLETE verification steps cite evidence.

Architecture to build

```
code/
  main.py               # entry: python3 code/main.py → ./output.csv
  ingest/               # one parser per format → Observation rows
    sql.py              # sqlite3 in-memory executescript, per-replica snapshot
    json_records.py, logs.py, text.py
    media.py            # VLM extraction for PNG/PDF, cached to cache/media/*.json
  identity.py           # current + historical emails/phones/hashes/user_id, normalization
  intent.py             # multilingual deletion-vs-not classifier (LLM + cache + rule fallback)
  state.py              # as-of(audit_at) latest-state per (system, resource)
  policy.py             # category → rule → finding/remediation/verification ops
  planner.py            # ordering, step numbering, JSON serialization
  prompts/*.md          # all prompts in markdown (code judge reads these)
  evaluation/
    main.py             # scores against sample_output + custom cases
    custom_cases/       # your ≥3 hand-built cases
    evaluation_report.md, usage_report.md
```

Use LLMs in only three places:

1. Intent classification (`claude-haiku-5-5`): 518 short texts in multiple languages, temperature 0, cached.
2. Image and PDF extraction (`claude-sonnet-5-5` vision): 15 files, run once and cached as JSON.
3. Optional adjudicator for ambiguous identity links.

Total cost stays tiny, runs are reproducible, and the design is easy to defend in the AI interview. Log `usage` from every API response into a run ledger so `usage_report.md` is generated from real numbers.

Where the points actually are

* Evidence-citation tie-breaking: decide which file to cite when several prove the same state. Derive this from the samples, not intuition.
* Replica drift: a primary can show a record deleted while a reporting or failover replica still has it. Each replica copy is its own finding.
* Recreation paths: an active `data_flow_*` or a restorable backup makes a case INCOMPLETE even if every record is gone.
* Decoys: near-identical emails and unrelated users in the global activity stream. Match on grounded identifiers only.
* NOT_APPLICABLE: export, correction or opt-out requests that are worded like deletions. These have zero sample coverage, so your custom cases matter most here.
